# Commission workflow release checklist

This is a local implementation checklist, not evidence of a live deployment. The changes in `supabase/migrations/20261011000000_commission_reference_public_id.sql`, `20261011010000_private_commission_workflow.sql`, `20261011020000_atomic_deliverable_release.sql`, `20261011030000_artwork_publication.sql`, `20261011040000_artist_workspace.sql`, and `20261013000000_owner_session_revocation.sql` have **not** been applied to an external database in this task. Keep public commission submission disabled until the isolated-service checks below pass.

## Implemented paths

- Guest inquiry uses a server-generated request reference and a bearer tracking token whose hash is stored on the commission. Opening the link exchanges the token for a scoped, HttpOnly cookie. Rotation invalidates the previous token.
- JPG, PNG, WebP and PDF reference files go through the server validator into the private `commission-private` Supabase bucket. A one-time claim attaches each staged file to an inquiry. Stale unclaimed files are removed by the authenticated cleanup job. Owner and customer file access creates 60-second signed URLs only after authorization.
- The owner sends a versioned quote with price, scope, terms, delivery date and revision allowance. The customer accepts that version before a checkout token is issued; acceptance and its timeline event commit in one database transaction. The old direct approve/reject endpoints return `410` for authenticated callers; the current owner UI uses the event-backed action route.
- Razorpay order attachment and captured payment recording use database RPC transactions. The webhook stores an event receipt and retries on persistence failure. Refund ledger, captured-payment status and event acknowledgement are committed together by `record_commission_refund`; a late `refund.created` cannot reverse a processed refund. Owner reconciliation fetches the gateway order and payments before recording a missing capture.
- Commission and payment timeline records feed customer tracking and owner views. Notification jobs have dedupe keys, a five-minute claim lease, retries and Resend idempotency keys. If Resend is absent, jobs remain pending.
- The new atomic transition migration writes commission status, timeline, audit, and notification outbox records together. Customer submission retries repair missing initial events/outbox rows. Deliverable release timestamps, delivery state, event, audit, and notice are committed together. Apply the new migration before using these transitions.
- Admin payments, analytics, audit and operational settings pages use persisted records and server-side owner authorization. Artwork views represent approximate view events, not unique visitors. Traffic source is not collected and is therefore not shown as measured data.
- Admin artwork management supports multiple optimized images, a primary image, independent draft/publication/sale states, archival, confirmed draft deletion, and staged museum wall slots. The public exhibition reads published placements only. Publishing staged placements runs in one database transaction. Storage cleanup failures are surfaced for manual review.
- The owner login uses Supabase TOTP enrollment or challenge after password sign-in. Private owner reads and sensitive writes require an `aal2` session and an active Supabase session row. The password-only login bootstrap returns authorization status without private data. A server-to-server admin API secret remains a separate privileged credential and must never be exposed to a browser or shared with third parties.
- The inbox derives unread customer-event counts from persisted event/read state, and the owner can save, edit, apply, and delete quote templates. Templates fill scope, terms, and revision allowance only; price and delivery date remain request-specific.

## Environment and deployment sequence

1. Back up the current Supabase database and Storage metadata, confirm a restore procedure, and record the current deployment revision. Apply migrations in filename order to a disposable Supabase project first. Inspect SQL errors, existing rows, RLS/grants, and the private bucket with anon, customer, and service-role clients. Only then schedule the same migrations for the intended production project. The migration adds tables and changes the commission status constraint; rollback requires a reviewed data-aware migration or database restore, not blind drops.
2. Configure `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_EMAIL` for the owner login (and optionally `ADMIN_NOTIFICATION_EMAIL` for alerts), Razorpay test-mode `RAZORPAY_KEY_ID`, `RAZORPAY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `NEXT_PUBLIC_RAZORPAY_KEY_ID`, `CRON_SECRET`, and canonical HTTPS `NEXT_PUBLIC_SITE_URL`. Configure `RESEND_API_KEY` and verified `RESEND_FROM_EMAIL` for mail. Configure Upstash URL/token for distributed rate limits. Keep service keys server-only. Rotate exposed keys if any were previously published.
3. Schedule authenticated GETs for `/api/cron/notification-jobs`, `/api/cron/cleanup-staging`, and the existing expiry cleanup endpoint, using `Authorization: Bearer <CRON_SECRET>`. Monitor failed/pending notification jobs and received payment events.
4. In Razorpay **test mode**, run a complete approved-quote checkout and verify the gateway order, payment, database ledger, status, timeline and notification. Repeat for failed/cancelled checkout, delayed/duplicate/out-of-order callbacks, DB outage followed by webhook retry or owner reconciliation, partial refund, full refund and over-capture/mismatched payload. Never send a real charge or refund during these checks.
5. Test a real Resend message, provider rejection, retry after worker interruption and deduplication. Check that tracking links use the canonical domain and no permanent private file URL appears in email, public HTML or analytics.
6. Review and approve customer-facing quote, cancellation, revision, usage-rights, privacy/retention and refund policies before launch. The current quote terms are entered per request; the application does **not** encode a universal legal refund policy or initiate refunds automatically. A refund request is review-only until the owner acts in the gateway.
7. Test owner login, TOTP enrollment/challenge, session renewal, logout and manual recovery with the intended account. Revoke a session and confirm sensitive writes fail; test a non-owner and an `aal1` owner session. Establish a safe Supabase administrator recovery procedure for a lost authenticator before launch. Test customer A versus B tracking/file access, token rotation, upload MIME/content/size/count limits, stale cleanup, deliverable access and mobile/desktop interaction in an isolated service environment. Capture audit logs and provider IDs without logging tokens or secrets.
8. In the disposable project, create/edit a draft with multiple images, confirm it is absent from anonymous catalog reads, publish it, stage/rearrange wall slots, preview as owner, publish/unpublish the exhibition, archive/restore it, and permanently delete an unlinked draft. Check actual storage objects, generated thumbnails, RLS, audit records, invalid-slot rejection, and cleanup after a forced database/storage failure.
9. Configure error monitoring, backup alerts and webhook retry visibility. For rollback, stop new commission submissions/checkouts, retain gateway webhook delivery and ledger data, revert the application deployment, and restore only after reconciling captured gateway payments. Do not remove new tables or private files while live payments may still reference them.

### Fixes completed in this continuation

- Owner authorization now checks verified email, provider MFA assurance, verified JWT subject/session ID and the restricted is_owner_session_active RPC. Deleted, expired, foreign or unverifiable sessions deny access. MFA and session checks are the default for private owner reads as well as writes. The data-free login bootstrap works without constructing a service-role client.
- New session migration 20261013000000_owner_session_revocation.sql checks auth.sessions with a fixed empty search path and service-role-only execution. Provider sign-out/access-token replay still requires an actual disposable Supabase lifecycle test; local tests prove the application and SQL decisions, not the provider lifecycle.
- Fixed the revision allowance guard to recognize the actual revision_requested event (and the older action spelling). Real SQL reproduced the previous bypass and now rejects exhausted allowances.
- Read acknowledgements carry the latest customer timestamp shown to the owner. SQL preserves messages arriving after that snapshot and rejects future boundaries. The route accepts Supabase timestamp offsets as well as UTC Z values.
- Next.js build/tracing roots now point at the repository. Browser tests identify the existing production-minified R3F controller through its props rather than function name, wait for the fully streamed commission form, use the existing article card structure, and close browser sessions reliably. No carousel/illustration source changes were made in this continuation; file hashes confirm preservation.
